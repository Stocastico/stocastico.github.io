# CLAUDE.md — Project Guide

## Project Overview

Personal website of **Stefano Masneri** (Senior AI Engineer), hosted on GitHub Pages at `stocastico.github.io`. ES-modules-based site bundled with Vite; no framework.

## Tech Stack

- **HTML/CSS/JS** — vanilla, no framework
- **Vite** — dev server + production bundler (multi-page input)
- **Three.js** (npm, bundled by Vite) — 3D globe (travel page only). The hero is Canvas2D, so the homepage ships no Three.js
- **Node.js ^20.19 || >=22.12** — the range Vite 8 requires; scripts and tests use the built-in test runner, zero test dependencies. CI runs 24.
- **Playwright** — E2E UI tests (dev dependency)

## Coding Conventions

- **ES modules everywhere** — `js/` and `data/` directories have nested `package.json` with `"type": "module"`. Generator scripts and tests for them stay CJS.
- **Test mocking for Three.js** — modules subscribe to `onChange` from `js/three-context.js`; tests call `__setThreeForTests(mock)` / `__resetThreeForTests()` (re-exported from `js/main.js`) to swap the active THREE.
- All generator scripts support `--dry-run`, `--help`, and standard CLI flags
- Generated files (`data/cv.js`, `data/locations.js`, `js/theme.js`, and the `@theme-generated` block in `css/styles.css`) should never be edited manually
- Tests use Node.js built-in test runner (`node --test`) — no Jest, no Mocha
- YAML source files → JS ESM data files via generator scripts
- Self-hosted fonts (no Google Fonts CDN). **Three faces, four roles** (Montaggio, #190). **Archivo** (variable, weight 300–800 × width 62–125, 71 KB subset) is `--font-display` — set **condensed (`font-stretch: 62%`) and 800** for the hero name, section titles, `.globe-title`, `.post-title` — and `--font-ui` at normal width for chrome: nav links, `.btn`, `.social-btn`, chips, tags, eyebrows, labels. The tagline uses its other extreme, **expanded 300**, so one family shows both ends of its width axis one above the other; that axis is most of the file's weight, and clipping it to 62–100 would save 21 KB and lose the design. **JetBrains Mono** stays as `--font-mono`, but only for things that are data — years, kernel weights, keyboard keys, the MNIST lab's numbers. It used to lead the whole system (display *and* chrome *and* metadata), which made every label on the site read as code and is one of the commonest looks on the generated web. **Source Serif 4** is `--font-prose`: paragraphs, card descriptions, and `.project-card__title`. Display and UI hold the same family deliberately — they answer different questions, so either swaps at one line. Chrome is **sentence case**: the uppercase-tracked labels (`.stat-label`, `.contact-label`, `.project-tag`, `.skill-panel-title`, …) lost their `text-transform` and tracking, and `.section-tag` is a timeline-style track label (a colour chip plus a word in `--text-muted`) rather than an eyebrow. The hero canvas reads weight, width and family off the `<h1>` (`stretchKeyword()` maps the computed percentage to the keyword a canvas font accepts), so changing the CSS changes the grid. Note `--font-sans` was **renamed to `--font-prose`**; a variable named `-sans` holding a serif is a lie that rots
- `prefers-reduced-motion` is respected everywhere — all animations degrade gracefully

## Testing layers

See `docs/TESTING.md` for the full rationale. In short:

- **`npm test`** — 1,100+ assertions: pure functions, generator round-trips, drift checks on generated artefacts, static analysis over source, and DOM-stubbed behaviour. Fast, and **structurally blind to anything that needs a rendered page**.
- **`test/contrast.test.mjs`** — measures the shipped palette rather than trusting the eye (it measured four palettes × dark and light until #188 cut the site to one theme). Text pairs against WCAG 2.1 AA; surface pairs against an **OKLab lightness step**, because a contrast ratio cannot express one threshold that is meaningful in both light and dark mode. Imports `SURFACE_ALPHA` from `scripts/generate-theme.js` so the two can't drift.
- **`test/e2e/budget.e2e.mjs`** — a **gzip byte ceiling** on the two files every page downloads (`main-*.js` ≤ 14 KB — 10.7 KB after the redesign, lowered from 20 in #195 — and `main-*.css` ≤ 17 KB), plus a string probe asserting no `data/*` module is inside the shared chunk and that the heavy lazy chunks are still separate files. The build gated on behaviour, CSP hashes, card drift and analytics — never on size, which is how 21.3 KB gzip of data came to ride along on all 21 pages unnoticed. Budgets sit ~25% above current; raising one is a deliberate edit, which is the point. The probe is the sharper of the two: re-adding a static `import '../data/unesco.js'` fails it while staying inside the byte headroom.
- **`test/e2e/a11y.e2e.mjs`** — **axe-core** (WCAG 2.1 A + AA) over every built page, and the main pages again at phone width with the menu open. Browser-layer because the interesting failures are computed, not written: composited contrast, resolved accessible names, focusability. It scrolls each page and waits for the reveal before running — axe skips what it considers hidden, so an unscrolled page reports a clean bill of health for content it never looked at. Best-practice rules are excluded on purpose. It found a real bug on its first run: `.link-chip-count` faded text with `opacity: 0.7` over an already-muted colour, which composited below 4.5:1 in every light palette. That is the precise blind spot of `test/contrast.test.mjs`, which pairs colour *tokens* against surfaces and cannot see an opacity applied afterwards — **never de-emphasise text with `opacity`**, use a validated colour token.
- **`test/e2e/`** — real Chromium against the built `dist/`. This layer exists because four shipped bugs were all invisible to the layer above: content stuck at `opacity: 0`, a page torn down on a bfcache freeze, and a map drawn in its background colour. Covers the reveal invariant (nothing on screen may be invisible — after scrolling, after landing on an anchor, after clicking each nav link, at three widths), no-JS and reduced-motion paths, **content pushed outside the viewport**, console errors, 404s, theme + palette switching, the bfcache round trip, and the MNIST lab. The page list is read from `dist/`, so a new page is covered automatically.

  **The viewport check is worded that way on purpose, and it used to be "horizontal overflow".** It asserted `documentElement.scrollWidth <= clientWidth`, which `overflow-x: clip` on `html`/`body` (css/styles.css §2) makes permanently true: a clip container is not a scroll container, so its scrollWidth is its clientWidth no matter what sticks out of it. Measured — a 3000px-wide `<div>` injected into a 390px viewport left scrollWidth at 390 and the assertion green. Fifteen pages × three viewports of assertions, none of which could fail, and the per-element "name the widest offender" loop underneath the early return was unreachable code. Two live bugs went through the gap: the navbar clipped between 681 and 835px (the ⌘K chip up to 146px off-screen, "Contact" gone below ~705px, both still keyboard-focusable — WCAG 2.4.7/2.4.11), and the five-column table on `projects/aroundtheworld.html` whose last column started 15px past the right edge of a phone. **Clipping is not overflow**: the question has to be asked of each element about the viewport, never of the document about itself. Elements inside an ancestor that deliberately clips or scrolls are exempt, and that ancestor walk stops *before* `body` — including it would mark everything "handled" and hand the test back its no-op. A canary test plants a 3000px element and requires the detector to see it, because what silently disabled this last time was a stylesheet change nowhere near the test.

**Every generated artefact has a drift guard, and the list is the point.** The pattern is always the same — regenerate in memory from the source of truth, compare to what is committed, fail with the command that fixes it. It is checked for: `data/cv.js`, `data/locations.js` (name-set correspondence, not bytes — the generator geocodes, so a byte-exact regeneration would need the network), `data/countries.js`, `data/unesco.js`, `data/links.js`, `data/lenet-weights.js`, `data/hero-scan.js`, the nautical chart in `travel.html`, `js/theme.js`, the `@theme-generated` blocks in `css/styles.css`, the world-map SVG in `index.html`, the SSR'd card/timeline/accordion/grid/total blocks, the CSP hashes, the analytics pixel, the speculation rules, `public/llms.txt` and `public/sitemap.xml`. `public/feed.xml` is deliberately checked by shape rather than bytes (git dates move on every commit) — see the note in `test/feed.test.mjs`.

Four of those guards were added after a mutation sweep found they did not exist: `css/styles.css` and `js/theme.js` (the theme tests only ever exercised the generator's functions against fixtures, so changing the shipped `--accent` by one digit passed), `data/countries.js` and the world-map SVG (a country could silently change category on the homepage map) (and a theme-toggle block that no longer exists). **If you add a generator, add its drift guard in the same commit** — and confirm it by breaking the artefact and watching the suite go red, because a drift test written against an already-consistent pair is exactly the kind that passes without checking anything.

**A CSS change needs a picture, not just a green suite.** Run `npm run screenshots` and look at the result at 390, 768 and 1440 before opening a PR. This is not belt-and-braces: the last two bugs to reach visitors were both visual and both passed every assertion in the repo. The navbar clipped between 681 and 835px — the ⌘K chip up to 146px off-screen, "Contact" gone entirely below ~705px, on all 21 pages — and the five-column table on `projects/aroundtheworld.html` lost its last column off the right edge of a phone. 954 static and 62 browser assertions were green through both, and three consecutive audits read the stylesheet without seeing either. What found them was looking at a screenshot. Note the harness is only useful because it now waits for `scrollY` to settle before shooting; before that the capture named `index-hero-*.png` was a photograph of the Projects section, which is its own version of this lesson.

**Which layer does a new test belong in?** If the question can be answered by reading a file, it goes in `npm test`. If it can only be answered after `npm run build`, it goes in `test/e2e/build-output.e2e.mjs` — not behind a `skip:` in the static suite. `test/cname.test.js` used to guard `dist/CNAME` with `skip: fs.existsSync(distDir) ? false : '…'`, which reads as a courtesy and behaves as a deletion: every workflow runs `npm test` *before* `npm run build` (deliberately — a two-second static failure should land before a five-minute browser run), so `dist/` never existed when that test was evaluated and it was skipped in CI every single time. It guarded the custom-domain binding, and it had opted itself out. **A test that skips on whether an artefact happens to exist is indistinguishable from a deleted test, and reports success either way.** If answering it requires knowing where something landed on screen, what colour it painted, or what the browser did to the page, only `test/e2e/` will do. **Both layers run on every pull request**, from `.github/workflows/e2e.yml` — the one workflow with a `pull_request` trigger. `npm test` runs there ahead of the Chromium install (it is ~2 s, so a drift check fails the job immediately rather than after the five-minute browser run), then the browser suite. Both also gate the deploy (`deploy.yml`). Before this, `npm test` was gated *only* on `push: [main]`, so a PR could sit green with every static assertion red and the first sign of it was the deploy refusing to publish after the merge — a safe failure on the wrong side of the merge button. If you add a `pull_request` workflow, remember that the check name `Browser tests` is what a status check resolves against.

## Workflow Rules

1. **Always run `npm test` after changes** to verify nothing breaks
2. **After editing `data/cv.yaml`**, run `npm run generate-cv` (and `npm run generate-sea-chart` if `places:` or a career entry changed — the travel chart reads both)
3. **After editing `data/locations.yaml`**, run `npm run generate-locations`. If countries changed, also `npm run generate-countries --refresh` then `npm run generate-world-map` (and review `data/countries.yaml`).
4. **After editing `data/palettes.yaml`**, run `npm run generate-theme`, then `npm run generate-favicons` to rebuild the raster icons, then `npm run generate-project-og` (the project social cards are palette-driven) and `npm run generate-og` (the site card). There is **one palette and one theme** (#188): `generate-theme` rejects a `light:` variant, and there is no toggle or picker to keep in step any more. The homepage world map needs no regeneration — it uses CSS `var(--*)` classes.
5. **After changing `data/land-50m.json`, `CHART_BOUNDS` (js/utils.js), the CV's `places:`/career or `data/locations.yaml`**, run `npm run generate-sea-chart`. The `generate-sea-chart` test fails on drift in CI.
6. **After editing `data/countries.yaml`**, run `npm run generate-countries` then `npm run generate-world-map` (rewrites the inline SVG block in `index.html`).
7. **After editing `data/unesco.yaml`**, run `npm run generate-unesco`.
8. **After editing `data/links.yaml`**, run `npm run generate-links`.
9. **After editing `data/projects.js`, `data/publications.js`, `data/cv.yaml`, `data/unesco.yaml` or `data/links.yaml`**, run `npm run generate-cards` to refresh the static content baked into `index.html`, `projects.html`, `publications.html`, `cv.html`, `travel.html` and `links.html`. (For the three YAML sources, run their own generator first — `generate-cards` reads the generated `data/*.js`.) The `generate-cards` test fails on drift in CI.
10. **After re-running `npm run train-cnn`**, run **both** `npm run generate-lenet-weights` and `npm run generate-hero-scan` — the interactive page loads the first, the homepage hero's Learned filter the second, and both derive from the same `data/cnn-model.json`. The `lenet-weights` and `hero-scan` tests fail on drift in CI. (`data/cnn-samples.json` is no longer shipped by the hero; `test/hero-scan.test.mjs` uses it to check the kernels against the full model.) Training downloads MNIST into `.cache/mnist/` (gitignored); none of it ships to the browser.
11. **After adding/removing a project page** (or any HTML page), run `npm run generate-analytics` and `npm run generate-speculation-rules`, then `npm run generate-csp-meta`, so the new page carries the GoatCounter pixel, the speculation rules and the CSP `<meta>`. Run **generate-csp-meta last**, after anything that changes inline `<script>` content (`generate-project-jsonld`, `generate-cards`, `generate-speculation-rules`) — the CSP hashes each inline script (`script-src` uses per-page `'sha256-…'` instead of `'unsafe-inline'`), so a changed JSON-LD or rules block invalidates the hash. The `seo`/`html-quality`/`analytics`/`speculation-rules`/`csp` tests gate this in CI.
11. Production builds are produced by GitHub Actions (`.github/workflows/deploy.yml`) on push to `main` — Vite builds `dist/` and the official Pages action publishes it.

## Important Patterns

- **Email obfuscation**: Contact email is base64-encoded in HTML `data-*` attributes, revealed by JS on click
- **Globe data pipeline**: `locations.yaml` → geocode via Nominatim API (cached in `.cache/`) → `locations.js` (ESM module that also assigns `globalThis.LOCATIONS` so legacy bare-global reads keep working)
- **Project pipeline**: Write Markdown with YAML frontmatter → `node scripts/new-project.js file.md` → generates HTML + updates `data/projects.js`
- **Static card rendering**: Project cards and publication items are **server-rendered into static HTML** (not just JS-injected) so crawlers and no-JS visitors see real content. `generate-cards` (`scripts/generate-cards.mjs`) bakes them between `<!-- generated:project-cards -->` / `<!-- generated:publication-items -->` markers — newest 3 **work** projects / featured papers on `index.html`, all on `projects.html` / `publications.html` — plus a `CollectionPage` JSON-LD on `publications.html`. Markup comes from the shared pure builders in `js/render-cards.js`, which `js/main.js` also uses, so SSR and client markup can't drift (`generate-cards` test guards it). On load, `renderProjects()` re-shuffles the homepage set; `renderPublications()` honours `data-render="all"` on `publications.html`.

  **The same treatment now covers `cv.html`, `travel.html` and `links.html`** (`<!-- generated:cv-timeline -->`, `generated:cv-skills`, `generated:unesco-accordion`, `generated:links-grid`), with builders in `js/render-page.js`. They were the counter-example to the rule for a long time: rendered only in the browser, they shipped as a navbar, a footer, meta tags and an empty `<div>` — `dist/cv.html` was 12 KB with zero career content, on the highest-stakes page of a site whose contact copy invites job offers, and all three were advertised in `sitemap.xml`. Nothing looked wrong, because everything looks right to anyone running JS. Two consequences worth keeping straight. **(1) The builders return arrays of lines, not one string** — `replaceBlock` indents them so the committed HTML stays diffable, and `js/main.js` joins them with `\n`; every element involved is block-level or inside a grid/flex container, so that whitespace creates no boxes and the two paths render identically. **(2) The client still re-renders on load** rather than adopting the SSR'd DOM. That is deliberate for `links.html`, where `wireLinksFilter()` assumes a DOM it built; it also keeps one code path instead of two. Tests read the *committed* markup (escaped via `escapeHtml`, since skill names carry `&`) rather than calling the builder and comparing it to itself, plus a blunt "no generated block is near-empty" check — a builder that silently returns nothing would otherwise pass a drift test comparing empty to empty.

  **`generated:unesco-total`** (also `js/render-page.js`) is the running count of visited World Heritage sites, on the travel page directly under the copy that states the 1,200+ goal. It is generated rather than typed for the reason the whole page is: the number moves whenever `data/unesco.yaml` gains a site, and a hand-typed one said **100** through the entire period the United States was filed under **Europe** — a wrong number stated confidently, which is worse than no number. Note the near-empty check's floor is **per-block** since this landed: every other block is a list where 200 chars is below one entry, but this one is a single sentence at ~139 chars, and lowering the global floor to fit it would have quietly halved the protection on the six list blocks. There is also a direct assertion that the rendered figure equals the number of sites in the data — a byte count cannot tell 112 from 100.
- **Work vs. personal projects** (issue #136): every entry in `data/projects.js` carries a **required** `kind` — `'work'` (professional or research: Vicomtech, Fraunhofer, MPI, the PhD) or `'personal'` (a side project). - **LeNet-5 training pipeline**: `scripts/train-cnn.mjs` trains a small LeNet-5 (28×28 → conv 6@5×5 → pool → conv 16@5×5 → pool → 120 → 84 → 10; ~44 k params, 98.27 % test accuracy) on MNIST **plus 122 real digits captured from the interactive page** (`--real-train`, mixed in at 7 % of the set) in **plain JavaScript with no dependencies**, writing `data/cnn-model.json` + `data/cnn-samples.json`. Two flags make a long run survivable where a single command is capped at ten minutes: `--checkpoint f.json` writes weights **and momentum buffers** after every epoch, `--resume f.json` picks up from there. Epoch order and augmentation are seeded from (SEED, epoch), so a split run reproduces an unsplit one. `--real-eval none` is the explicit way to train with no held-out captures; any other missing path is now an error rather than a silent `n/a`. The trained model feeds two consumers: the interactive page (`generate-lenet-weights`, int8, the full forward pass) and the homepage hero's Learned filter (`generate-hero-scan`, conv1 only). Training is deliberately a separate step from both generators, so they stay deterministic, network-free and CI-runnable. - **Interactive MNIST page** (`projects/mnist-lenet.html`, issue #113): the inverse of the hero. The hero shows one convolution at a time and borrows at most conv1's six kernels, because the homepage must not pay for an ML runtime; this page runs the **real forward pass in the browser** on whatever the visitor draws. Three pieces make that cheap. (1) **One forward pass, two hosts** — `js/lenet.js` holds `forward()` and nothing else Node-specific, so `scripts/lib/lenet.mjs` (training: init, backward, float32 (de)serialisation) and `js/mnist-lab.js` import the identical code. A second implementation would eventually disagree with the weights it was trained against and the failure would read as a bad model rather than a bug. (2) **int8 weights** — `generate-lenet-weights` quantises the five weight tensors to int8 with a per-tensor symmetric scale and leaves the five bias vectors in float32 (236 numbers; a quantised bias shifts a whole channel). 237 KB of float32 JSON becomes ~61 KB of ESM, ~44 KB gzip, and predictions on the ten committed samples are unchanged (max |Δp| ≈ 9e-3). (3) **Lazy everything** — `js/main.js` gates the dynamic `import()` on `#mnist-lab`, so the weights, the samples and the lab are three chunks no other page fetches; verified by build output and a Playwright request check. **The preprocessing is the part that decides whether this works.** MNIST is not raw 28×28: crop to the ink's bounding box, scale the longest side to 20 px preserving aspect, then centre in the 28×28 field **by centre of mass**. The centring target is `FIELD / 2 + 0.5 = 14.5`, not 14.0 — MNIST translates by whole pixels onto index `28 // 2`, i.e. the *centre* of pixel 14. With 14.0 a committed MNIST digit reconstructs to a mean absolute error of 18/255 and the model misreads two of ten; with 14.5 nine of ten round-trip byte-for-byte. `test/mnist-preprocess.test.mjs` pins that round trip, which is a far stronger check than asserting the output is 784 bytes. Colour: the drawing canvas strokes in the palette accent and the model reads the **alpha** channel, so the ink colour cannot change a prediction. `_resolveInk()` picks between the `*Hi` and plain accent shades by measured luminance against `theme.bg`, so it stays right if the palette ever changes. (The re-tint on a theme switch went with the switch, #188.)

- **Scroll-driven animations**: the **reading-progress bar** is a CSS scroll-progress timeline (`animation-timeline: scroll(root block)`), not JavaScript. Guarded by `test/e2e/content.e2e.mjs` — necessarily browser-layer — and those tests must wait for `window.scrollY` to settle: `html` has `scroll-behavior: smooth`, so a fixed timeout after `scrollTo()` measures mid-flight.

  **There used to be a hero parallax as well, and it is gone with the old hero** (#189). Two lessons from it are worth keeping. - **Forced colours**: there is a `@media (forced-colors: active)` block **outside `@layer`**, immediately above the print block and for the identical reason — the palette lives on an unlayered `:root`, and a layered block cannot repoint `--text`. Its load-bearing rule is the same one print needs: `.hero-name`, `.section-title` and `.globe-title` paint their letterforms from a gradient via `background-clip: text` + `-webkit-text-fill-color: transparent`, and forced-colors overrides `color` but **not** `text-fill-color` — so in Windows High Contrast the hero name and every section heading were simply invisible. - **Print**: the `@media print` block sits **outside `@layer`** on purpose — the palette is defined on an unlayered `:root`, and unlayered normal declarations beat every layered one regardless of specificity, so a print block inside `@layer components` can restyle elements but silently fails to repoint `--text`. It repoints the palette (white surfaces, near-black text, darkened accents) rather than enumerating selectors, and resets the gradient-filled headings (`.hero-name`, `.section-title`, `.globe-title`) which otherwise print as ghosts because backgrounds are not printed. (`.photo-initials` used to be in that list; it went when the about photo became a real `<img>`, and the selector exists nowhere any more.) It also resets `.tagline-word` / `.tagline-sep`, which are **not** `[data-animate]`: `initTaglineReveal()` splits the hero tagline into spans that start at `opacity: 0` and are restored only by a CSS animation, so printing inside the first ~675 ms printed the site's one-line statement of purpose as blank. The general rule the print block encodes three times over now: **anything whose visibility waits on an animation or an observer needs a print reset**, because printing neither scrolls nor waits.
- **llms.txt**: `public/llms.txt` is a plain-text index for AI assistants and answer engines — every top-level page with its description, every project with kind/year/description, and the publication count. **Generated** (`scripts/generate-llms.mjs`), not hand-written, and for the same reason the sitemap is: a hand-maintained index of a site that gains a project page every few months is wrong within the year, and being confidently wrong to a machine reader is worse than being absent. - **CSP**: every page ships a `Content-Security-Policy` `<meta>` (generated by `scripts/generate-csp-meta.mjs`, marker-wrapped). `script-src` carries **per-page `'sha256-…'` hashes** of each inline `<script>` (JSON-LD + speculationrules) instead of `'unsafe-inline'`; `style-src` keeps `'unsafe-inline'` (inline `style=""` attributes can't be hashed). `test/csp.test.mjs` recomputes the hashes and fails on drift, so re-run `generate-csp-meta` after any change to inline scripts.
- **Speculation rules**: `scripts/generate-speculation-rules.mjs` injects a marker-wrapped `<script type="speculationrules">` into all 21 pages. It used to be **hand-written on `index.html` alone, matching only `/projects/*`** — so `projects.html`, the page that lists all fifteen projects, speculated nothing, and no nav destination was ever warmed from anywhere. The split between the two rule types is not stylistic: **`prerender` fetches subresources and runs the page, `prefetch` fetches the document only**, and this site counts traffic with a no-JS `<img>` pixel. A prerender therefore *loads that pixel*, recording a visit to a page nobody opened; GoatCounter does filter speculative loads, but in `filter()` inside `count.js` — the JS integration this site deliberately avoids. So `prerender` stays scoped to `/projects/*` (the pre-existing rule, and the pre-existing caveat), and the site-wide rule is `prefetch`, which cannot fire the pixel, cannot pull Three.js on `travel.html`, and cannot pull the int8 weights on the MNIST page. Both use `eagerness: "moderate"` (hover/pointerdown), so nothing speculative happens until the visitor aims at something. The `prefetch` rule excludes `/projects/*` explicitly because `*` crosses path segments in a URL pattern — `/*.html` matches `/projects/foo.html` too, and a URL matching both rules is fetched twice. `test/speculation-rules.test.mjs` fails on drift, on a page missing the block, on `prerender` widening beyond `/projects/*`, on an `eagerness` bump, and on a CSP hash that no longer matches the block — **but only since the generator got a main guard.** Its inject loop ran at the top level, so `import`ing the module did the same thing as running it, and the test imports it on its first line: every assertion was made about files the import had just rewritten. Flipping both `eagerness` values in `now.html` to `"eager"` left all 45 assertions green. See the note on Analytics below for the second half of the damage.
- **Analytics**: cookieless GoatCounter via a **no-JS `<img>` pixel** (no external `<script>`, no cookies, no personal data). `scripts/generate-analytics.mjs` injects a marker-wrapped `<img src="https://stocastico.goatcounter.com/count?p=…&t=…">` into every HTML page (`p` = canonical path, `t` = page `<title>`), wrapped in `<!-- generated:analytics -->` markers like the CSP/JSON-LD generators. Its drift guard ("the committed block must equal a fresh generation") was therefore comparing a file it had just regenerated against a fresh generation, and could not fail: deleting the GoatCounter `<img>` from `now.html` outright left all 45 assertions green, because the import put it back. `generate-speculation-rules.mjs` had the identical defect.

  The second half is worse than the blind test. **`npm test` was writing to the working tree.** A suite that repairs the drift it is meant to report will repair it in CI too, so a page that had lost its pixel would deploy with the pixel silently restored and no signal that anything had gone wrong. Tests read; generators write. Every generator now ends with `if (process.argv[1] && fileURLToPath(import.meta.url) === path.resolve(process.argv[1])) main();` (or `require.main === module` in the CJS ones) — check that guard exists before importing a generator from a test, and there is a cheap standing check: `npm test` must leave `git status` unchanged.
- **Performance**: **the favicon is static markup and no JavaScript touches it**. `initAnimatedFavicon()` in `js/main.js` used to draw a capital "S" onto a 64px canvas after `document.fonts.ready` and write the PNG over the first `link[rel="icon"]`. It is deleted, because it could only ever disagree with the icon set the site ships: every static artefact — `public/favicon.svg`, the inline `data:` URI in each page's `theme:start` block, `favicon.ico`, the four PNGs and the maskable pair — draws **"SM" in Georgia**, all regenerated from the active palette by `generate-theme` / `generate-favicons`, while the canvas drew a different letter in a different face. So on any JS-enabled visit the tab icon disagreed with the bookmark, the PWA icon and the OS icon set. It also imported the dark `THEME` statically rather than resolving `getTheme()`, and never listened for `themechange` — light mode kept the dark square and a palette switch left the old accent, which is why `THEME_LIGHT.faviconBg` / `faviconFg` existed with **no consumer at all**. `js/main.js` no longer imports from `js/theme.js`. The globe caches its canvas bounding rect (invalidated on scroll/resize) rather than calling `getBoundingClientRect()` per `mousemove`.
- **Page teardown / bfcache**: `js/main.js` collects disposables in `_disposables` and runs `destroy()` on each at `pagehide` — **but only when `event.persisted` is false** (`initLifecycleCleanup`). A `pagehide` with `persisted: true` means the browser is freezing the page into the back/forward cache, not unloading it: Back restores that document intact, with no reload and no `DOMContentLoaded`, so anything destroyed on that event never comes back. Destroying unconditionally was a real bug — Back returned a page whose hero canvas, navbar, ⌘K palette and back-to-top were all dead (Chrome has bfcached same-site navigations since 96). A frozen page is not a leak: its rAF loops are paused and resumed by the browser, its listeners are what make the restore work, and an evicted entry is discarded whole. Every canvas class already resumes via its own `visibilitychange` handler. The chrome inits — `initNavbar`, `initMobileMenu`, `initBackToTop`, `initCommandPalette` (js/ui.js) and the observer inits `initScrollReveal`/`initCounters` — **return a teardown fn**, wired via `_pushTeardown(...)`. In ui.js they register every document/window listener + observer through a `listenerBag()` (`on()` / `add()` / `teardown()`) so nothing leaks into the bfcache. WebGL/Canvas classes (globe, receptive-field, mnist-lab) instead expose `destroy()` and track listeners in a `_listeners` array. **Any new init that adds a document/window listener or observer must return a teardown and be `_pushTeardown`-ed.**
- **Full-bleed world map**: the `<figure class="world-map-figure">` on the homepage lives **outside** `.container`, directly under `<section id="places">` — the one element allowed to break the frame. Every other section sits at the same width, so this is the single deliberate break in the rhythm. Capped at `max-width: 1600px` because the viewBox is ~2.5:1 and width drives height. If you re-run `generate-world-map`, the markers move with the figure; the generator keys off `<!-- world-map:start … -->` and re-indents to wherever they sit.
- **Scroll reveal is load-bearing, not decoration**: `[data-animate]` is `opacity: 0` until `initScrollReveal()` (js/animations.js) adds `.visible`, so anything that reveal misses is invisible **permanently and silently** — markup present, section rendering as an empty band, no error anywhere. Two causes did exactly that: `content-visibility: auto` on `#projects`/`#publications`/`#contact` (a skipped subtree IntersectionObserver cannot see into — at 390px it left all six animated elements in `#contact` at opacity 0 forever, and every nav-anchor jump landed on a blank section), and `threshold: 0.1` + a negative `rootMargin`, which an element already scrolled past on arrival can never satisfy. The property is gone (see the note in css/styles.css §17) and the reveal is now defensive: `threshold: 0`, a **sweep** that reveals anything whose top has reached the viewport bottom regardless of what the observer reported (re-run on scroll/resize/`hashchange`/`load`, detaching once nothing is pending), an instant reveal for elements above the viewport, everything shown at once under `prefers-reduced-motion` or with no `IntersectionObserver`, and `data-delay` clamped to 320 ms (generate-cards bakes `i * 70`, so publications.html's last paper carried 2520 ms of blank row). The CSS hidden state sits inside `@media (scripting: enabled)` so a no-JS visitor still sees the server-rendered cards, and `@media print` re-reveals everything with `opacity: 1 !important` — **printing scrolls nothing**, so none of the sweep's events fire and Ctrl+P on a freshly-landed page printed 21 of 21 animated elements on the homepage (9 of 12 on the CV) as blank space. Right layout, right page count, missing ink. The fix belongs in CSS rather than in a `beforeprint` handler or a reveal-all timer: opacity is a paint concern, print is a media, and a timer still loses to someone printing immediately. Guarded by `test/css-assets.test.mjs` + the reveal tests in `test/main.node.test.mjs`. **Never hide content behind an observer callback without a fallback that reveals it.** The same trap bites again whenever content is injected *after* `initScrollReveal()` has collected its targets: moving the data modules behind dynamic `import()` made every renderer asynchronous, and the nodes they created carried `data-animate` with nothing observing them — all fifteen project cards and all thirty-seven publications rendered as an empty band, permanently and silently. **Any async render into a `[data-animate]` container must call `revealNewContent(container)`** (js/animations.js), which adds the new nodes to the live observer and sweeps, or shows them outright when no reveal is active. The browser suite caught this; nothing in the static suite could have.

  **The counters were the same trap on `textContent` rather than opacity.** `initCounters()` (js/ui.js) zeroed all three About stats at `DOMContentLoaded` so the count-up had a start value, and restored them only when the observer fired at 60% visibility. Printing scrolls nothing, so Ctrl+P on a freshly-landed homepage printed "0 Countries / 0+ Publications / 0+ Years Exp." — and unlike the reveal, **no stylesheet can fix this**, because the real numbers were gone from the DOM. The `@media print` rule that rescues opacity has no equivalent for text. So the reset now happens *inside* the observer callback, immediately before the count-up that undoes it: the server-rendered value stands until something is actually going to animate it. `prefersReducedMotion()` sets the final value outright, and a missing `IntersectionObserver` leaves the markup alone. **Never overwrite server-rendered content at init for the benefit of an animation that may never run.** Guarded in `test/e2e/content.e2e.mjs`, which asserts under `emulateMedia({ media: 'print' })` *without scrolling first* — scrolling would fire the observer and hide the bug.

- **Section headers**: every `.section-header` is **left-aligned** and its `.section-tag` is a plain uppercase eyebrow — *not* a pill, and never centred. The centred kicker-pill-over-display-title pattern is the single strongest "generated landing page" tell, and the whole site was using it five times over. Sub-page toolbars (`.links-toolbar`, `.links-count`) follow the same left edge.
- **Heading rank is a structure, not a size.** `cv.html` ran `h1` → `h3` for a long time: the timeline cards and the skill panels are all `h3` (`js/render-page.js`) and the page's only other heading was its `h1`, so the one page built to be *skimmed* had a level skip in it. Two `visually-hidden` `h2`s ("Career and education", "Skills") now sit outside `#cv-timeline` / `#cv-skills` — outside, so `renderCV()`'s `innerHTML` rewrite on load cannot take them away, and hidden because the eyebrow, the `h1` and the legend already say it visually three times over. **axe classes `heading-order` as best-practice and `test/e2e/a11y.e2e.mjs` excludes those on purpose**, so the browser layer is blind here by design — the same blind spot that left the globe a11y list at `h4` under an `h1`, and that let `links.html` ship 48 blogroll cards whose names were `<span>`s, one heading on the whole page. Two checks in `test/html-quality.test.mjs` cover it now: **no page may skip a heading rank**, and **a linked card repeated 5+ times must contain a heading**. The second is grouped by card class and thresholded on purpose — a blanket "any class ending in `-name`/`-title` must be a heading" rule was written first and is wrong, because it fires on `.unesco-name` (already inside a `<summary>`), `.skill-item-name` and `.lang-name`, none of which are destinations. What makes a link card different is that it *is* one; three `.contact-card`s under an existing `h2` are chrome and stay below the threshold. Both strip HTML comments before matching. The older `has exactly one <h1>` check in the same file does **not**, so a literal heading tag inside a comment still makes that one page claim two `h1`s — the identical trap the 404 forced-colors note hit with a literal style tag.
- **Title + nav conventions**: `<title>`/`og:title`/`twitter:title` use ` — Stefano Masneri` (em-dash) on **project detail pages** and ` | Stefano Masneri` on the **homepage + top-level pages**; keep each tier consistent. `generate-project-jsonld` strips either separator before deriving the JSON-LD `headline`/breadcrumb. Nav links to the CV page use `cv.html` (label "CV") — the homepage no longer has a `#skills` section (removed, see below) or a `#research` id (removed earlier). Every page carries a "Now" nav item (`now.html`), the `.cmd-trigger-hint` ⌘K chip after the nav list, and an Atom `<link rel="alternate">` in the head — a feed reader pointed at any URL on the site should find the feed, not just the homepage. Footer reads "Written by me, coded with Claude and plenty of ☕ in San Sebastián" — the wording deliberately separates authorship of the words from authorship of the code (no Three.js credit — the homepage ships none). One page drifted to "Made with Claude" and stayed that way unnoticed; the wording is the same on all 21 or it says nothing.

  **The nav holds eight links, and the burger breakpoint is a measurement, not a round number.** "Publications" was added because 37 papers and a PhD were reachable only from one paragraph on the homepage — the biggest hole in the site's architecture for an academic profile, and the ⌘K palette had listed it all along while the visible bar did not. Adding that one `<li>` re-created the exact clipping bug documented in `css/styles.css` §navbar: the bar's intrinsic width went past the viewport and the ⌘K chip hung off the right edge at every width from 901 to 980, with "Contact" gone below 901. So the burger breakpoint moved **900 → 1024** and the chip's paired `min-width` **901 → 1025**; the two must always move together. **If you add a ninth link, measure again** — sweep viewport widths asking each navbar element whether its own right edge is past the viewport, and remember that `overflow-x: clip` makes the document-level version of that question permanently answer "fine".
- **Homepage Expertise section — removed**: the homepage used to duplicate the CV's skills as 37 ungrouped tag pills under `#skills`; `cv.html`'s skills panel (`data/cv.yaml` → `skills:`) says the same thing with more depth (proficiency tiers, CEFR language levels) and is now the single source of truth. The section, its CSS (`.skills-split`, `.skills-sticky-header`, `.skill-group*`, `.skill-tag*`), and its `.skill-group` entry in the `initCardTilt` selector (`js/animations.js`) are gone; the nav item that pointed at `#skills` now points at `cv.html` instead, so there's still a one-click path to the fuller skill list.

- **Maintenance automation**: two scheduled jobs, both deliberately low-noise. (There was a third — the weekly palette rotation — deleted for the reasons under the pinning note below.) `.github/dependabot.yml` groups npm and GitHub-Actions updates into one monthly PR each — nothing else was watching the five dependencies, and monthly-grouped is the cadence at which a solo maintainer still reads them. `.github/workflows/link-check.yml` runs `npm run check-links` on the 1st and **opens an issue** rather than failing anything: two blogroll links had rotted unnoticed (one apex serving no certificate, one host simply gone — about 4% in eighteen months). The script's difficulty is entirely in what counts as dead. 401/403/405/429 are filtered as bot-blocking, not breakage — `whc.unesco.org` 403s every automated request and would otherwise file 130 false positives a month — and every URL gets three attempts, because an egress proxy that cannot reach an origin answers on the origin's behalf with its own 5xx. That produced a real false positive during development: `addi.ehu.eus` reported `HTTP 503` from a sandbox and is perfectly healthy in a browser. **That same host is now the sole entry in `SKIP_HOSTS`** — it has since been put behind a human-verification layer, so an automated request no longer gets a status at all, it hangs until the timeout on all three attempts and reads exactly like a dead host (issue #173). A skip is the last resort and is deliberately not silent: the report prints the URL and the reason, and `test/check-links.test.mjs` fails once no curated link points at a skipped host, so an entry cannot outlive the link it was written for — a skipped host is a link nobody is watching any more, which is the same rot the script exists to catch. **Never make this a PR gate.** A dead third-party link disappoints a visitor; it does not break a build, and gating 80 external hosts buys flakiness for no safety.

- **Two licences, and the boundary between them is the point**: MIT in `LICENSE` covers the code, CC BY 4.0 in `LICENSE-CONTENT.md` covers the prose and the hand-curated data. CC BY is the most permissive Creative Commons licence that still requires attribution — no NC, no SA, no ND — which is the right trade for a site whose text is the part worth reading. Three things worth keeping straight. **(1) `LICENSE` stays pure MIT text.** GitHub's licence detection matches the file against the canonical wording, so a preamble explaining the split would cost the repo its "MIT" badge; the split is explained in `README.md` and in `LICENSE-CONTENT.md`, never at the top of `LICENSE`. **(2) The exclusion list is the load-bearing half.** Not everything here is his to relicense: the fonts are SIL OFL 1.1 subsets (provenance is in the header of `css/fonts.css`), `data/countries-110m.json` / `data/land-50m.json` are world-atlas (ISC) over Natural Earth (public domain), and `data/publications.js` is metadata about papers whose copyright sits with publishers. The photo and the CV/thesis PDFs are deliberately reserved — free to read, not licensed for reuse. A content licence that silently swept those in would be an over-claim on other people's work. **(3) The site itself says nothing about either licence yet.** CC BY works by notice, and the footer carries only "© Stefano Masneri"; if the terms should reach a reader rather than only a cloner, that footer line is where they go — on all 21 pages at once, since the footer wording is identical everywhere by convention.

## Things to Avoid

- Don't bypass Vite — production HTML uses `<script type="module" src="/js/main.js">`; data files are imported by main.js, not loaded as standalone scripts
- Don't edit generated files (`data/cv.js`, `data/locations.js`, `js/theme.js`, `data/countries.js`, `data/unesco.js`, `data/links.js`, `data/hero-scan.js`, `data/cnn-model.json`) or the `<!-- world-map:start … -->` SVG block in `index.html` — regenerate via the relevant script
- **Inline architecture diagrams**: all seven architecture diagrams are **inline `<svg class="diagram">` in their project pages**, not `<img src="…svg">` and not raster. An external SVG is its own document and cannot read the page's custom properties, so its colours have to be baked in — and they were, across three files, in **three different superseded palettes** (indigo/cyan on `#080c14` for the RAG pair, crimson for brand-stadium). In light mode those were near-black rectangles in a cream page; in dark mode, *cold* blue-black on a warm brown one in accents the ramp never uses. Inlined, `fill="var(--accent)"` resolves like any other declaration, so they follow the palette and the light/dark toggle with **no regeneration step** — the same reason the homepage world map is inline. There is deliberately no generator: once the colours are variables there is nothing to generate. They also asked for `Inter` and `Segoe UI`, neither of which the site loads; they now use the mono stack, at 88% of the original size so the longest label stops overflowing its box. Two SVGs (`rag-query`, `mnist-lenet`) are *also* used as project-hero wallpaper, where a diagram behind a 65–95% scrim came out as grey wash with label text bleeding into the nav. Those files are now **stencils** — background rect removed — painted through `mask-image` with `var(--accent)` via `.project-hero--diagram`, so only their alpha matters. `test/css-assets.test.mjs` fails on a hex literal returning to an inline diagram, on one reverting to `<img>`, and on a diagram source nothing inlines — the `<img>` check derives its name list from `drafts/diagrams/` rather than hardcoding it, which the previous version did and which is why it said nothing about the four diagrams added later.

  **Four more arrived as raster, and raster has the identical bug with no way to inline it.** `mlops-architecture`, `mlops-pipeline`, `clear-architecture` and `clear-design-objectives` were `.webp` exports, two baked on a near-black ground and two on white — so in light mode the MLOps pair were black slabs in a cream page, and in dark mode the cleAR pair were glaring white ones, in accents (purple, cyan, orange, blue) the site's ramp has never contained. Exactly the failure the paragraph above records, surviving in the one form where `fill="var(--accent)"` cannot reach it. They are redrawn as SVG in `drafts/diagrams/` and inlined with `!svg()`. Two consequences worth keeping. **(1) The sources live in `drafts/`, not `img/`** — they are build-time input like `data/land-50m.json`, never deployed, and putting them in `img/` would trip the unreferenced-image check, since nothing ships them. **(2) `clear-architecture.webp` survives as hero wallpaper only.** It is the page's `bg`, painted under a 65–95% scrim where it is texture rather than information, so it does not have to stay in sync with the diagram it used to be; the other three were body-only and are deleted. The redrawn cleAR objectives diagram drops the stock-art avatars for labelled boxes, because the site's other diagrams are geometric and typographic and a clip-art schoolchild is not something `var(--accent)` can recolour either.
- Don't hardcode colours — add them to `data/palettes.yaml` and consume via `var(--*)` (CSS) or `THEME` from `js/theme.js` (JS/shaders), so palette switching stays consistent
- Don't colour small text with `var(--accent)` / `var(--accent2)` / `var(--accent-hi)`. Those are brand colours held to WCAG's **3:1 non-text** floor (gradients, borders, pins, glows). Text under 24px needs **4.5:1** and must use `var(--accent-text)` / `var(--accent2-text)`, which `test/contrast.test.mjs` validates against every surface it lands on — including hover states, where `--accent-hi` is *less* contrasty in light mode. Text on an accent **fill** uses `var(--on-accent)`, never `var(--bg)`
- Don't measure a text colour against `--bg` alone. Translucent surfaces **stack**: a card is `text` at 12% over the page, a `--bg-card-hov` chip inside a card composites twice, and cards sit on `bgAlt` as well as `bg` — each step lighter in dark mode. `textSurfaces()` in `test/contrast.test.mjs` enumerates the real set, measured from the rendered page; extend it rather than assuming
- Don't add a test file and assume it runs. `npm test` is a **glob** (`test/*.test.js test/*.test.mjs`) precisely because the hand-written list drifted: `test/theme-rebuild.test.mjs` was written, committed, and never named in it, so three assertions guarding the blank-canvas-after-theme-switch regression sat in the repo for months without CI ever executing them. Don't go back to enumerating files.
- **The palette no longer rotates, and `active:` is pinned.** A scheduled job (`.github/workflows/rotate-palette.yml`) used to advance `data/palettes.yaml`'s `active` key every Monday, regenerate, run both suites, commit to `main` and deploy. It is deleted, along with `scripts/rotate-palette.js` and its test. The reasoning: a visitor sees one palette and has no way to learn it ever changes, so the feature's entire audience was the maintainer — while its costs were real and recurring. An unattended weekly commit to `main` is a commit every open branch must merge, which is exactly what forced the palette-owned `<head>` lines into one `theme:start` block after a copy edit and a rotation collided one line apart; and a returning reader finding a differently-coloured site is the opposite of what repetition is for. (The runtime picker that replaced it is gone too, since #188 — see "One theme, no switch".)

- Don't bake a `path.relative()` result into a generated file. Four generators (locations, countries, links, unesco) write a "Generated by … from `<source>`" header, and `path.sep` made that header a function of the machine rather than the input: `data/locations.js` was committed from a Windows run naming `data\locations.yaml`, so every run on Linux or in CI rewrote the line back — a standing one-line diff in the file the project tells you never to hand-edit. Route it through `toPosix()` (`scripts/lib/paths.js`); `test/locations-generator.test.js` fails on a backslash surviving into any `data/*.js` header, so a fifth generator copying the old pattern is caught too.
- Don't edit the `@theme-generated` block inside `css/styles.css` by hand — it's overwritten by `generate-theme`
- Don't put the same fact in `README.md` and `CLAUDE.md`. **README is the map; this file is the reasoning.** README answers "what is this, how do I run it, what do I edit and what do I run afterwards" and links onward; everything about *why* a thing is the way it is, and every trap that has been fallen into once, belongs here. They used to overlap heavily — README was 52 KB of per-script flag documentation and feature description, nearly all of it a worse copy of what is below — and the duplication was not free: the same wrong claim about `test/analytics.test.mjs` ("fails on drift", when its own import made that impossible) sat in *both* files and was corrected in neither for weeks. README is 7 KB now and points at `--help` for flags, which is the only reference that cannot drift because it is generated from the code that runs. `docs/` holds the long-form reference (DATA-FORMATS, DEPLOYMENT, TESTING); when it goes stale, delete rather than deprecate — a 37-line frontmatter schema for a blog that never existed, and instructions for a `npm run minify` script that no longer does, both survived in `docs/` for months because nobody was reading them closely enough to notice they described nothing.
- Don't load external fonts, third-party scripts, or any cookie-setting / cross-site tracker — privacy-first. The one permitted external request is the **GoatCounter no-JS analytics pixel** (cookieless, no personal data, image-only — `img-src https://stocastico.goatcounter.com`); keep analytics to that pixel.
- Don't remove `prefers-reduced-motion` checks or accessibility attributes
- Don't commit `.cache/` changes without verifying geocoding results
- Don't add `module.exports` / CJS to anything under `js/` or `data/` — they're ESM
- Don't add a document/window listener or observer in an init without returning a teardown and `_pushTeardown`-ing it (bfcache leak); use `listenerBag()` in js/ui.js
- Don't statically `import` a **data** module (`../data/*.js`) into `js/main.js` either — the code rule below was learned for the (since deleted) 2D Europe map and then not applied to data. All six data modules were static imports, putting **21.3 KB gzip of a 31.3 KB shared bundle (68%)** on all 21 pages: a visitor on `now.html` fetched the UNESCO tree, the 49-entry blogroll, every travel pin, the full CV, 37 publications and 14 projects. Each renderer already gated on a DOM id, so the `import()` moved inside that gate — `main.js` is now 13.1 KB gzip and `now.html` pulls 16.2 KB of JS against 35.9 KB before. Consequence: the render functions take their data as a **required parameter with no default**, because a default has to name the module at the top of the file, which is what put it in the eager graph. `data/locations.js` rides along with the globe/Europe-map imports since both read `globalThis.LOCATIONS` from their constructors. `test/main.node.test.mjs` fails on a static `../data/` import *and* on a missing dynamic one, so deleting the imports does not satisfy it.
- Don't statically `import` a module that only one page uses into `js/main.js` — that puts it in the eager graph of **every** page. The 2D Europe map (`europe-map.js`, since replaced by the travel chart) was imported that way and shipped 10 KB to the twenty pages with no `#europe-canvas`. Single-page modules go behind a dynamic `import()` at their init site, like `globe.js` / `receptive-field.js` / `mnist-lab.js`
- Don't make `dist/img/` a copy of `img/`. `copyReferencedImages()` in `vite.config.js` copies **only what the built HTML names with an absolute `/img/` URL**, plus all of `img/og/` (one social card per palette — the inactive ones become the referenced one when `active:` changes). The old plugin walked the directory, so Rollup's hashed copy in `dist/assets/` and a verbatim copy both shipped: **28 byte-identical duplicates, 1,378 KB**, on top of **546 KB nothing referenced at all**. `dist/img/` is now 1.2 MB, down from 2.6 MB. The set is *derived* by scanning `dist/**/*.html` rather than hardcoded, so adding a project page needs no edit here. **11 files still ship twice on purpose** (~543 KB) — a hero background is hashed by Rollup *and* named by `og:image`, and pointing `og:image` at the hashed name would change the social-card URL on every build, busting scraper caches for a saving smaller than the problem. `test/css-assets.test.mjs` fails on any image in `img/` that nothing references.
- Don't add a `data/*.json` file expecting Vite to publish it — `copyDataJson()` in `vite.config.js` uses an explicit `RUNTIME_DATA_JSON` allowlist. Copying the whole directory published 356 KB nothing fetched (the float32 `cnn-model.json` among it). Add a file there only when something `fetch()`es it at runtime
- Don't hand-edit `theme_color`/`background_color` in `public/manifest.webmanifest` — `generate-theme` owns them (guarded by `theme-sync`)
