# CLAUDE.md — Project Guide

## Project Overview

Personal website of **Stefano Masneri** (Senior AI Engineer), hosted on GitHub Pages at `stocastico.github.io`. ES-modules-based site bundled with Vite; no framework.

## Tech Stack

- **HTML/CSS/JS** — vanilla, no framework
- **Vite** — dev server + production bundler (multi-page input)
- **Three.js** (npm, bundled by Vite) — 3D globe (travel page only). Both hero backgrounds are Canvas2D, so the homepage ships no Three.js
- **Raw WebGL/GLSL** — noise-gradient hero background
- **Node.js >= 18** — scripts and tests (built-in test runner, zero test dependencies)
- **Playwright** — E2E UI tests (dev dependency)

## Coding Conventions

- **ES modules everywhere** — `js/` and `data/` directories have nested `package.json` with `"type": "module"`. Generator scripts and tests for them stay CJS.
- **Test mocking for Three.js** — modules subscribe to `onChange` from `js/three-context.js`; tests call `__setThreeForTests(mock)` / `__resetThreeForTests()` (re-exported from `js/main.js`) to swap the active THREE.
- All generator scripts support `--dry-run`, `--help`, and standard CLI flags
- Generated files (`data/cv.js`, `data/locations.js`, `js/theme.js`, and the `@theme-generated` block in `css/styles.css`) should never be edited manually
- Tests use Node.js built-in test runner (`node --test`) — no Jest, no Mocha
- YAML source files → JS ESM data files via generator scripts
- Self-hosted fonts (no Google Fonts CDN). **Two faces, three roles** — the mono leads. **JetBrains Mono** is both `--font-display` (hero name, section titles, `.link-card-name`, the CNN hero's verdict digit) and `--font-mono` (metadata: eyebrows, tags, years, domains, stat labels, keyboard hints, CNN captions) *and* UI chrome (nav links, `.btn`, `.social-btn`, `.link-chip`). The two variables hold the same stack deliberately — they answer different questions, so a future display face swaps at one line. **Source Serif 4** is `--font-prose`: paragraphs, card descriptions, and `.project-card__title` (full-sentence titles that a monospace would blow out — length decides, not rank). Prose never gets the mono. Note `--font-sans` was **renamed to `--font-prose`**; a variable named `-sans` holding a serif is a lie that rots
- `prefers-reduced-motion` is respected everywhere — all animations degrade gracefully

## Testing layers

See `docs/TESTING.md` for the full rationale. In short:

- **`npm test`** — ~780 assertions: pure functions, generator round-trips, drift checks on generated artefacts, static analysis over source, and DOM-stubbed behaviour. Fast, and **structurally blind to anything that needs a rendered page**.
- **`test/contrast.test.mjs`** — measures every palette (dark *and* light) rather than trusting the eye. Text pairs against WCAG 2.1 AA; surface pairs against an **OKLab lightness step**, because a contrast ratio cannot express one threshold that is meaningful in both light and dark mode. Imports `SURFACE_ALPHA` from `scripts/generate-theme.js` so the two can't drift.
- **`test/e2e/budget.e2e.mjs`** — a **gzip byte ceiling** on the two files every page downloads (`main-*.js` ≤ 20 KB, `main-*.css` ≤ 17 KB), plus a string probe asserting no `data/*` module is inside the shared chunk and that the heavy lazy chunks are still separate files. The build gated on behaviour, CSP hashes, card drift and analytics — never on size, which is how 21.3 KB gzip of data came to ride along on all 21 pages unnoticed. Budgets sit ~25% above current; raising one is a deliberate edit, which is the point. The probe is the sharper of the two: re-adding a static `import '../data/unesco.js'` fails it while staying inside the byte headroom.
- **`test/e2e/a11y.e2e.mjs`** — **axe-core** (WCAG 2.1 A + AA) over every built page in **both themes**. Browser-layer because the interesting failures are computed, not written: composited contrast, resolved accessible names, focusability. It scrolls each page and waits for the reveal before running — axe skips what it considers hidden, so an unscrolled page reports a clean bill of health for content it never looked at. Best-practice rules are excluded on purpose. It found a real bug on its first run: `.link-chip-count` faded text with `opacity: 0.7` over an already-muted colour, which composited below 4.5:1 in every light palette. That is the precise blind spot of `test/contrast.test.mjs`, which pairs colour *tokens* against surfaces and cannot see an opacity applied afterwards — **never de-emphasise text with `opacity`**, use a validated colour token.
- **`test/e2e/`** — real Chromium against the built `dist/`. This layer exists because four shipped bugs were all invisible to the layer above: content stuck at `opacity: 0`, a page torn down on a bfcache freeze, and a map drawn in its background colour. Covers the reveal invariant (nothing on screen may be invisible — after scrolling, after landing on an anchor, after clicking each nav link, at three widths), no-JS and reduced-motion paths, horizontal overflow, console errors, 404s, theme + palette switching, the bfcache round trip, and the MNIST lab. The page list is read from `dist/`, so a new page is covered automatically.

**Which layer does a new test belong in?** If the question can be answered by reading a file, it goes in `npm test`. If answering it requires knowing where something landed on screen, what colour it painted, or what the browser did to the page, only `test/e2e/` will do. CI runs `npm test` on build + deploy, and the browser suite on every push/PR *and* as a deploy gate (`.github/workflows/e2e.yml`).

## Workflow Rules

1. **Always run `npm test` after changes** to verify nothing breaks
2. **After editing `data/cv.yaml`**, run `npm run generate-cv`
3. **After editing `data/locations.yaml`**, run `npm run generate-locations`. If countries changed, also `npm run generate-countries --refresh` then `npm run generate-world-map` (and review `data/countries.yaml`).
4. **After editing `data/palettes.yaml`** (or switching the `active` palette), run `npm run generate-theme`, then `npm run generate-favicons` to rebuild the raster icons. Every palette must define a nested `light:` variant (validated by `generate-theme`); the active palette's dark + light pair is what ships. After structural HTML changes to the theme toggle, run `npm run generate-theme-toggle` then `npm run generate-csp-meta` (the bootstrap script is CSP-hashed). If you **added or recoloured a palette**, also run `npm run generate-og` to (re)render its social card. The homepage world map needs no regeneration — it uses CSS `var(--*)` classes; per-palette OG cards are committed static files and `generate-theme` just repoints `og:image` at the active one.
5. **After editing `data/countries.yaml`**, run `npm run generate-countries` then `npm run generate-world-map` (rewrites the inline SVG block in `index.html`).
6. **After editing `data/unesco.yaml`**, run `npm run generate-unesco`.
7. **After editing `data/links.yaml`**, run `npm run generate-links`.
8. **After editing `data/projects.js`, `data/publications.js`, `data/cv.yaml`, `data/unesco.yaml` or `data/links.yaml`**, run `npm run generate-cards` to refresh the static content baked into `index.html`, `projects.html`, `publications.html`, `cv.html`, `travel.html` and `links.html`. (For the three YAML sources, run their own generator first — `generate-cards` reads the generated `data/*.js`.) The `generate-cards` test fails on drift in CI.
9. **After re-running `npm run train-cnn`** (or editing `data/cnn-samples.json`), run **both** `npm run generate-cnn-activations` and `npm run generate-lenet-weights` — the hero replays the first, the interactive page loads the second, and they derive from the same `data/cnn-model.json`. The `cnn` and `lenet-weights` tests fail on drift in CI. Training downloads MNIST into `.cache/mnist/` (gitignored); none of it ships to the browser.
10. **After adding/removing a project page** (or any HTML page), run `npm run generate-analytics` and then `npm run generate-csp-meta` so the new page carries the GoatCounter pixel and CSP `<meta>`. Run **generate-csp-meta last**, after anything that changes inline `<script>` content (`generate-project-jsonld`, `generate-cards`) — the CSP hashes each inline script (`script-src` uses per-page `'sha256-…'` instead of `'unsafe-inline'`), so a changed JSON-LD invalidates the hash. The `seo`/`html-quality`/`analytics`/`csp` tests gate this in CI.
11. Production builds are produced by GitHub Actions (`.github/workflows/deploy.yml`) on push to `main` — Vite builds `dist/` and the official Pages action publishes it.

## Important Patterns

- **Email obfuscation**: Contact email is base64-encoded in HTML `data-*` attributes, revealed by JS on click
- **Globe data pipeline**: `locations.yaml` → geocode via Nominatim API (cached in `.cache/`) → `locations.js` (ESM module that also assigns `globalThis.LOCATIONS` so legacy bare-global reads keep working)
- **Project pipeline**: Write Markdown with YAML frontmatter → `node scripts/new-project.js file.md` → generates HTML + updates `data/projects.js`
- **Static card rendering**: Project cards and publication items are **server-rendered into static HTML** (not just JS-injected) so crawlers and no-JS visitors see real content. `generate-cards` (`scripts/generate-cards.mjs`) bakes them between `<!-- generated:project-cards -->` / `<!-- generated:publication-items -->` markers — newest 3 **work** projects / featured papers on `index.html`, all on `projects.html` / `publications.html` — plus a `CollectionPage` JSON-LD on `publications.html`. Markup comes from the shared pure builders in `js/render-cards.js`, which `js/main.js` also uses, so SSR and client markup can't drift (`generate-cards` test guards it). On load, `renderProjects()` re-shuffles the homepage set; `renderPublications()` honours `data-render="all"` on `publications.html`.

  **The same treatment now covers `cv.html`, `travel.html` and `links.html`** (`<!-- generated:cv-timeline -->`, `generated:cv-skills`, `generated:unesco-accordion`, `generated:links-grid`), with builders in `js/render-page.js`. They were the counter-example to the rule for a long time: rendered only in the browser, they shipped as a navbar, a footer, meta tags and an empty `<div>` — `dist/cv.html` was 12 KB with zero career content, on the highest-stakes page of a site whose contact copy invites job offers, and all three were advertised in `sitemap.xml`. Nothing looked wrong, because everything looks right to anyone running JS. Two consequences worth keeping straight. **(1) The builders return arrays of lines, not one string** — `replaceBlock` indents them so the committed HTML stays diffable, and `js/main.js` joins them with `\n`; every element involved is block-level or inside a grid/flex container, so that whitespace creates no boxes and the two paths render identically. **(2) The client still re-renders on load** rather than adopting the SSR'd DOM. That is deliberate for `links.html`, where `wireLinksFilter()` assumes a DOM it built; it also keeps one code path instead of two. Tests read the *committed* markup (escaped via `escapeHtml`, since skill names carry `&`) rather than calling the builder and comparing it to itself, plus a blunt "no generated block is near-empty" check — a builder that silently returns nothing would otherwise pass a drift test comparing empty to empty.
- **Work vs. personal projects** (issue #136): every entry in `data/projects.js` carries a **required** `kind` — `'work'` (professional or research: Vicomtech, Fraunhofer, MPI, the PhD) or `'personal'` (a side project). Two consequences, and both halves of each matter. **(1) The homepage is work only.** `homepageProjects()` in `js/render-cards.js` filters to `kind === 'work'` **before** the shuffle and before the 3-card cap, and it is called from *both* `renderProjects()` (js/main.js) and `generate-cards` — filtering in only one would serve a no-JS visitor or a crawler a different portfolio than a JS visitor gets. The predicate matches `'work'` positively rather than excluding `'personal'`, so in the browser a missing or misspelt kind drops an entry off the homepage instead of sneaking it on; the build catches that entry separately. **(2) `projects.html` shows everything, badging the personal ones** via `.project-card__kind` on the year's mono metadata line. Only the exception is badged — thirteen "work" labels would carry no information — and the badge is deliberately outlined/muted rather than accent-filled like `.project-tag`, because the tags say what a project is *about* and this says who it was *for*. **The field has no default.** `assertProjectKinds()` throws from `generate-cards` and `validateProjectFrontmatter()` rejects a missing/unknown `kind` in `new-project.js` (which keeps its own copy of the list, being CJS — a test asserts the two agree). A default would make a forgotten `kind` silently become `'work'` and reappear on the front page, which is the exact failure the field exists to prevent. There is deliberately **no work/personal filter control** on `projects.html`: with one personal project a "Personal" facet is a control that mostly disappoints. Tests: `test/generate-cards.test.mjs` asserts no personal title or URL appears inside the committed `index.html` card block — checked against the shipped HTML, not through `homepageProjects()`, so a bug in the filter can't make the test pass alongside it.
- **Off-site project entries** (issue #132): a project's `url` normally points at a `projects/*.html` detail page, but it doesn't have to. The **Donostia dataviz** lives in its own repo (`Stocastico/donostia-dataviz`), deployed as a GitHub Pages *project* site — and because this repo's `CNAME` puts the user site on the apex domain, it is already served from `/donostia-dataviz/` on the same origin. So the card links straight there with a root-relative path, and **there is no English detail page in between**: the piece introduces itself on its first screen (title, subtitle, its six sources, links to methodology and a working paper), so a write-up here would have been a second click that told the reader less than the destination does. Three consequences to keep straight. **(1)** The entry omits `bg` — that field is only read by a detail page (hero + `og:image`), so keeping it would ship an image nothing renders (`test/css-assets.test.mjs` already skips a `bg`-less entry). **(2)** The entry carries `lang: 'es'`, which `projectCardHtml()` turns into `hreflang` on the anchor **and nothing else** — `lang="es"` there would make a screen reader pronounce the English card title in Spanish. The card copy says "Written in Spanish" and the `#places` link says "(in Spanish)", so the language is visible as well as machine-readable. **(3)** `generate-sitemap` skips any `url` outside `projects/`, which is correct — this Vite build does not produce that page and must not claim it; discoverability is the other repo's job. The `ItemList` JSON-LD in `projects.html` is hand-maintained and *does* list it, since that one is a list of projects rather than a list of pages this build ships. No CSP change: `default-src 'self'` doesn't gate navigation, and it's the same origin anyway.
- **Homepage world map**: `data/countries.yaml` (lived/visited, derived from `locations.yaml` but hand-editable) → `generate-countries` → `data/countries.js`; then `generate-world-map` projects `data/countries-110m.json` to a static inline SVG (silhouette + highlighted-country paths) and rewrites the `<!-- world-map:start … -->` block in `index.html`. The land silhouette holds ~80% of the bytes, so it is Douglas-Peucker simplified (eps 0.4°, sub-pixel at the ~820px display width) and speck-sized islands are dropped — ~48% smaller SVG with no visible quality loss; highlighted countries are left at full detail. Fills use CSS `var(--pin-lived)` / `var(--pin-holiday)` classes, so a palette switch needs no regen. Micro-states absent from the 110m TopoJSON (e.g. Malta, San Marino, North Macedonia) stay in the data but don't render at world scale.
- **UNESCO accordion**: `data/unesco.yaml` (continent → country → site, https-only links) → `generate-unesco` → `data/unesco.js`; `renderUnescoAccordion()` in `js/main.js` builds a `<details>` disclosure tree, gated on `#unesco-accordion` (travel page only). The globe + Europe map init the same way — keyed off `#globe-canvas` / `#europe-canvas`, which now live only on `travel.html`.
- **Links blogroll**: `data/links.yaml` (a flat list; each entry has a name, an https-only url, optional `description`, one or more `categories`, and optional `tags` — categories/tags written as inline YAML flow arrays, e.g. `[ai, visual-explanation]`) → `generate-links` → `data/links.js`. The generator de-duplicates by URL (merging the categories/tags of duplicates) and emits `LINKS { categories: [{slug,label}], links: [...] }` with the used categories in canonical order. `renderLinks()` in `js/main.js` builds a category filter bar plus a single de-duplicated grid of `.link-card`s, gated on `#links-grid` (links page only); `linkMatchesFilter()` drives the client-side show/hide. https-only validation in the generator, HTML-escaped again at render. Category labels live in `CATEGORY_LABELS` in `scripts/generate-links.js`; unknown slugs are tolerated (humanised). Keep the list short and curated.
- **CNN hero pipeline**: `scripts/train-cnn.mjs` trains a small LeNet-5 (28×28 → conv 6@5×5 → pool → conv 16@5×5 → pool → 120 → 84 → 10; ~44 k params, 98.27 % test accuracy) on MNIST **plus 122 real digits captured from the interactive page** (`--real-train`, mixed in at 7 % of the set) in **plain JavaScript with no dependencies**, writing `data/cnn-model.json` + `data/cnn-samples.json`. Two flags make a long run survivable where a single command is capped at ten minutes: `--checkpoint f.json` writes weights **and momentum buffers** after every epoch, `--resume f.json` picks up from there. Epoch order and augmentation are seeded from (SEED, epoch), so a split run reproduces an unsplit one. `--real-eval none` is the explicit way to train with no held-out captures; any other missing path is now an error rather than a silent `n/a`. `scripts/generate-cnn-activations.mjs` then replays ten forward passes, quantises every layer's activations to uint8 against a shared per-layer max and base64-packs them into `data/cnn-activations.js` (~42 KB source, ~11 KB gzip). `js/cnn-hero.js` is a *player* for that data — it draws the layers in oblique projection and animates the signal travelling through them — so **the browser runs no inference and downloads no ML runtime**. Depth comes from three things. The **static recession** (`DEPTH_RISE` plus the `FOCAL`/`DEPTH_SPAN` perspective, `_view()`/`_project()`) is the one that survives a still screenshot: the pipeline runs *away* from the viewer, so each successive layer is drawn smaller and higher — the 28×28 input low and large in the foreground, the verdict high, small and far off. `RISE` anchors on `_layerCentre()`, which the hand-tuned `PLACEMENT` already puts on one flat y ≈ 220 line for all six layers, so the ramp alone establishes the staircase and nothing needs renormalising; it is split either side of that line so the composition stays centred in its box. The shrink is **not** a hand-set ramp — each layer carries a real depth coordinate (0 at the input, `DEPTH_SPAN` at the verdict) and its scale is the honest `FOCAL / (FOCAL + z)`, with the two constants chosen so the far end lands near 0.70. Everything routes through `_project()` — planes fold the scale into the cell size, so outline, cells and the plane-local line width shrink as one — which is why wires, captions and verdict follow for free. The caption strip deliberately stays **level** while the pipeline climbs away from it: it reads as the ground line the scene recedes over. The pointer then modulates this with two more effects. (1) **Turntable** (`TURN_RANGE`): because the layers are spread along the depth axis as well as across the picture, they are a set of points in the horizontal plane, and the pointer's x rotates that whole arrangement about the scene's vertical axis (`_sceneCx`). Each layer travels an arc of its own circle, and the signature of a real rotation falls straight out of re-projecting the rotated (x, z): the input sits in front of the pivot and the verdict behind it, so one swings right while the other swings left, and the near end grows as it comes toward the viewer while the far end shrinks. `_view()` keeps `cx` (the layout centre, which a layer's own geometry must still be measured from) separate from `tx` (where the rotation carried it), so at rest the transform is the identity and the tuned composition is reproduced exactly. The range can be generous because the geometry self-limits — swinging the input left also swings it away, and the resulting shrink very nearly cancels the extra travel, so its left edge barely moves further into the hero-copy mask. Note the planes' own lean (`SHEAR_X`) stays **fixed** through all of this: a rigid turntable would re-lean every card as it swung, which was tried and rejected — at this scale it turns a 28×28 digit into a diagonal ribbon and reads as wobble rather than rotation. Positions ride the wheel; card orientation does not. (2) **Vertical parallax** (`_depthFactor`, `LAYER_RECEDE`/`STACK_RECEDE`, `PAR_Y`): the share is **signed**, +1 at the input through 0 mid-pipeline to −1 at the output, so the two ends scissor about the scene's centre instead of drifting together. There is deliberately no horizontal counterpart — the turntable owns the x axis outright, and a second sideways term would only muddy the rotation. That is the reason the hero is hand-rolled rather than built on TensorSpace.js (Three.js + TensorFlow.js, several hundred KB, unmaintained). Training is deliberately a separate step from the generator, so the generator stays deterministic, network-free and CI-runnable; `test/cnn-activations.test.mjs` regenerates and fails on drift.
- **Interactive MNIST page** (`projects/mnist-lenet.html`, issue #113): the inverse of the hero. The hero is a *player* for offline-computed activations because the homepage must not pay for an ML runtime; this page runs the **real forward pass in the browser** on whatever the visitor draws. Three pieces make that cheap. (1) **One forward pass, two hosts** — `js/lenet.js` holds `forward()` and nothing else Node-specific, so `scripts/lib/lenet.mjs` (training: init, backward, float32 (de)serialisation) and `js/mnist-lab.js` import the identical code. A second implementation would eventually disagree with the weights it was trained against and the failure would read as a bad model rather than a bug. (2) **int8 weights** — `generate-lenet-weights` quantises the five weight tensors to int8 with a per-tensor symmetric scale and leaves the five bias vectors in float32 (236 numbers; a quantised bias shifts a whole channel). 237 KB of float32 JSON becomes ~61 KB of ESM, ~44 KB gzip, and predictions on the ten committed samples are unchanged (max |Δp| ≈ 9e-3). (3) **Lazy everything** — `js/main.js` gates the dynamic `import()` on `#mnist-lab`, so the weights, the samples and the lab are three chunks no other page fetches; verified by build output and a Playwright request check. **The preprocessing is the part that decides whether this works.** MNIST is not raw 28×28: crop to the ink's bounding box, scale the longest side to 20 px preserving aspect, then centre in the 28×28 field **by centre of mass**. The centring target is `FIELD / 2 + 0.5 = 14.5`, not 14.0 — MNIST translates by whole pixels onto index `28 // 2`, i.e. the *centre* of pixel 14. With 14.0 a committed MNIST digit reconstructs to a mean absolute error of 18/255 and the model misreads two of ten; with 14.5 nine of ten round-trip byte-for-byte. `test/mnist-preprocess.test.mjs` pins that round trip, which is a far stronger check than asserting the output is 784 bytes. Colour: the drawing canvas strokes in the palette accent and the model reads the **alpha** channel, so a palette switch cannot change a prediction; a theme change re-tints existing ink with `globalCompositeOperation = 'source-in'`, which preserves alpha exactly. `_resolveInk()` picks between the `*Hi` and plain accent shades by measured luminance against `theme.bg` rather than by reading `data-theme` — light palettes darken the plain shade for WCAG AA, so `*Hi` there would paint pale ink on a pale surface.
- **Hero background start**: the canvas builds itself on `requestIdleCallback(..., { timeout: 1500 })`, with the `mousemove`/`scroll`/`touchstart` listeners kept only as an **accelerator**. It used to wait for one of those events, which kept it off the critical path but made the site's best idea conditional on the visitor moving the mouse — a keyboard user, anyone reading without touching anything, every headless renderer, every social-preview fetcher and every print saw an empty rectangle. Idle time preserves the original goal (measured: the chunk is still requested after `main.js` and `main.css`, only 2 requests before the `load` event) while guaranteeing a paint at ~400 ms. **The timeout is the load-bearing part** — a busy main thread can defer an idle callback indefinitely, and browsers withhold it entirely on a page that never becomes interactive, which is exactly the headless case; `setTimeout` provides the same deadline where `requestIdleCallback` is missing.
- **Hero background selection**: `supportsCnnHero()` (js/utils.js) gates the CNN scene on `(min-width: 1100px) and (pointer: fine)` plus data-saver / slow-connection checks — narrower or touch-first viewports get `NeuralNetwork2D` instead. The branch happens **before** the dynamic `import()` in `js/main.js`, so phones never download the activation chunk. `rebuildNeural()` re-runs the choice on `themechange` and whenever the window crosses the breakpoint.

- **Theme pipeline**: `data/palettes.yaml` (one `active` key + named palettes) → `npm run generate-theme` → rewrites the `@theme-generated` `:root` block in `css/styles.css`, regenerates `js/theme.js`, and updates `<meta theme-color>` / inline favicon / nav-logo gradient across every `*.html` + `public/favicon.svg` + the `theme_color`/`background_color` in `public/manifest.webmanifest`. CSS reads `var(--*)`; the WebGL/Canvas2D modules and GLSL shaders import `THEME` + the `int()` / `rgba()` / `glvec()` helpers from `js/theme.js` (the shader source is a JS template literal, so colours are interpolated at module load — no recompile, no uniforms). Switching the whole site's palette = edit one YAML key + run one command. `generate-theme` also repoints every brand page's `og:image`/`twitter:image` at the active palette's social card (`img/og/og-<key>.png`, built by `scripts/generate-og.mjs` from the same palette colours via an SVG→PNG render with embedded fonts).
- **Runtime palette picker**: `generate-theme` emits, besides the active palette's `:root` block, a `@theme-generated-alt` block with every *other* palette scoped to `:root[data-palette="<id>"]` (plus its `[data-theme="light"]` pair), and exports `PALETTES` + `ACTIVE_PALETTE` from `js/theme.js`. The active palette is deliberately **not** re-emitted — it already is the `:root` default, so "select the active palette" means "remove the attribute". `applyPalette(id)` (js/ui.js) pins `data-palette`, persists to `localStorage['palette']`, repoints `<meta theme-color>` and fires the same `themechange` event the light/dark toggle uses, so the colour-baked canvases rebuild. The picker has two entry points: the ⌘K command palette under "Appearance", and — more discoverable — a row of palette-dot buttons (`.palette-dot`, one per `data/palettes.yaml` entry) sitting directly in the navbar next to the light/dark toggle, wrapped together in `.theme-controls`. Each dot is a static two-circle SVG swatch (accent/accent2, same motif as the ⌘K icon) baked by `scripts/generate-theme-toggle.mjs` reading `data/palettes.yaml` at generate time — no hex hand-authored, no runtime palette-table lookup needed for the colours themselves. `initTheme()` (js/ui.js) syncs each dot's `aria-pressed` to `resolvedPalette()` on load and on `themechange` (so picking a palette from ⌘K also updates the navbar dots), and wires their clicks to `applyPalette(id)`. The `<head>` bootstrap re-applies the stored id before first paint (pattern-checked, since it has no access to the palette table — an unknown id matches no rule and falls back to the default). **Known limitation**: the favicons and the OG card are committed per-palette static files, so they stay on the *active* palette regardless of the visitor's choice; the nav-logo gradient does follow it (its stops are `var(--accent)` / `var(--accent2)`, not baked hex).

- **The ⌘K palette ships on every page.** It used to be homepage-only: `index.html` carried `#cmd-overlay`, every other page carried the navbar and the key handler but no overlay, so `initCommandPalette()` returned early and Ctrl+K silently did nothing from the second page onward — a shortcut advertised in the navbar chip that dies on the first navigation. The overlay markup now sits in all 21 pages. Two consequences. **(1) Every destination in `SECTIONS`/`ACTIONS` is root-absolute** (`/projects.html`, `/docs/cv.pdf`) — a relative `projects.html` resolves to `/projects/projects.html` from a project detail page. Section entries with no `href` scroll to the element when the page has it and fall back to `/#<id>` when it doesn't, so "Contact" works from `now.html`. **(2) "Copy email" reads the base64 pair off `#cmd-overlay` itself** when no `.contact-email-obfuscated` card is on the page (only the homepage has one); same obfuscation-at-rest, just a second host for it. Guarded by `test/e2e/interaction.e2e.mjs`, which opens the palette on every page in `dist/` and asserts the list populated — so a new page is covered the moment it is built.
- **Light / dark theme**: every palette in `data/palettes.yaml` carries a **required nested `light:` variant** (a full palette body — light surfaces, dark text, accents darkened for WCAG AA). `generate-theme` emits **two** CSS blocks (the default dark `:root`, plus a `@theme-generated-light` override scoped to `:root[data-theme="light"]`) and exports `THEME` (dark default) + `THEME_LIGHT` + a `getTheme()` resolver from `js/theme.js`. **The site is dark by default regardless of OS preference** — light is strictly opt-in via the navbar toggle (no `prefers-color-scheme` auto-apply). The static HTML carries no `data-theme`; a `<head>` bootstrap script (injected by `scripts/generate-theme-toggle.mjs`, hashed into the CSP) re-applies a stored light/dark choice before first paint to avoid FOUC. `initTheme()` (js/ui.js) wires the navbar toggle (pins `data-theme`, persists to `localStorage`, updates `<meta theme-color>`, fires a `themechange` event). The colour-baked canvases — noise-gradient/neural-net hero and the travel-page globe/Europe map — resolve their palette via `getTheme()` at construction and are **rebuilt on `themechange`** (js/main.js) so they recolour live. Re-run `generate-theme-toggle` after adding a page (then `generate-csp-meta`).
- **Print**: the `@media print` block sits **outside `@layer`** on purpose — the palette is defined on an unlayered `:root`, and unlayered normal declarations beat every layered one regardless of specificity, so a print block inside `@layer components` can restyle elements but silently fails to repoint `--text`. It repoints the palette (white surfaces, near-black text, darkened accents) rather than enumerating selectors, and resets the gradient-filled headings (`.hero-name`, `.section-title`, `.globe-title`, `.photo-initials`) which otherwise print as ghosts because backgrounds are not printed.
- **llms.txt**: `public/llms.txt` is a plain-text index for AI assistants and answer engines — every top-level page with its description, every project with kind/year/description, and the publication count. **Generated** (`scripts/generate-llms.mjs`), not hand-written, and for the same reason the sitemap is: a hand-maintained index of a site that gains a project page every few months is wrong within the year, and being confidently wrong to a machine reader is worse than being absent. Page descriptions are lifted from each page's own `<meta name="description">` — one place to edit, and this file cannot disagree with what a browser is told. Note that meta attribute is **line-wrapped in the source**, so a single-line regex reads every description as empty (that mistake looked like a real finding during the review). `public/` is copied verbatim by Vite, so it ships with no plugin. `robots.txt` points at it. `test/llms.test.mjs` fails on drift, on a missing project, on an HTML entity or tag surviving into the plain text, and on any non-https link. Re-run after editing `data/projects.js` or any page description.
- **Atom feed**: `public/feed.xml` — one entry per project plus one for the `/now` page, generated by `scripts/generate-feed.mjs` (autodiscovery `<link>` in `index.html`). Entry timestamps come from git history (same policy as the sitemap's `<lastmod>`), and the `/now` entry's id embeds the page's own "Last updated" date so each update surfaces as a *new* entry in a reader. Because git dates move with every commit, `test/feed.test.mjs` checks shape and content — entry count, every project present, RFC 3339 dates, https-only, the `/now` date in sync with the page — rather than byte-for-byte drift. Re-run `generate-feed` after editing `data/projects.js` or the `/now` date.
- **CSP**: every page ships a `Content-Security-Policy` `<meta>` (generated by `scripts/generate-csp-meta.mjs`, marker-wrapped). `script-src` carries **per-page `'sha256-…'` hashes** of each inline `<script>` (JSON-LD + speculationrules) instead of `'unsafe-inline'`; `style-src` keeps `'unsafe-inline'` (inline `style=""` attributes can't be hashed). `test/csp.test.mjs` recomputes the hashes and fails on drift, so re-run `generate-csp-meta` after any change to inline scripts.
- **Analytics**: cookieless GoatCounter via a **no-JS `<img>` pixel** (no external `<script>`, no cookies, no personal data). `scripts/generate-analytics.mjs` injects a marker-wrapped `<img src="https://stocastico.goatcounter.com/count?p=…&t=…">` into every HTML page (`p` = canonical path, `t` = page `<title>`), wrapped in `<!-- generated:analytics -->` markers like the CSP/JSON-LD generators. The pixel's origin is allowlisted in the CSP `img-src` (`generate-csp-meta.mjs`). `test/analytics.test.mjs` guards the pixel + CSP origin on every page and fails on drift. View stats at `https://stocastico.goatcounter.com`.
- **Performance**: NoiseGradient renders 3 frames then stops; favicon is static. Globe/Europe-map cache their canvas bounding rect (invalidated on scroll/resize) rather than calling `getBoundingClientRect()` per `mousemove`.
- **Page teardown / bfcache**: `js/main.js` collects disposables in `_disposables` and runs `destroy()` on each at `pagehide` — **but only when `event.persisted` is false** (`initLifecycleCleanup`). A `pagehide` with `persisted: true` means the browser is freezing the page into the back/forward cache, not unloading it: Back restores that document intact, with no reload and no `DOMContentLoaded`, so anything destroyed on that event never comes back. Destroying unconditionally was a real bug — Back returned a page whose hero canvas, navbar, ⌘K palette and back-to-top were all dead (Chrome has bfcached same-site navigations since 96). A frozen page is not a leak: its rAF loops are paused and resumed by the browser, its listeners are what make the restore work, and an evicted entry is discarded whole. Every canvas class already resumes via its own `visibilitychange` handler. The chrome inits — `initNavbar`, `initMobileMenu`, `initBackToTop`, `initCommandPalette` (js/ui.js) and the observer inits `initScrollReveal`/`initCounters` — **return a teardown fn**, wired via `_pushTeardown(...)`. In ui.js they register every document/window listener + observer through a `listenerBag()` (`on()` / `add()` / `teardown()`) so nothing leaks into the bfcache. WebGL/Canvas classes (globe, europe-map, neural-net, noise-gradient) instead expose `destroy()` and track listeners in a `_listeners` array. **Any new init that adds a document/window listener or observer must return a teardown and be `_pushTeardown`-ed.**
- **Full-bleed world map**: the `<figure class="world-map-figure">` on the homepage lives **outside** `.container`, directly under `<section id="places">` — the one element allowed to break the frame. Every other section sits at the same width, so this is the single deliberate break in the rhythm. Capped at `max-width: 1600px` because the viewBox is ~2.5:1 and width drives height. If you re-run `generate-world-map`, the markers move with the figure; the generator keys off `<!-- world-map:start … -->` and re-indents to wherever they sit.
- **Scroll reveal is load-bearing, not decoration**: `[data-animate]` is `opacity: 0` until `initScrollReveal()` (js/animations.js) adds `.visible`, so anything that reveal misses is invisible **permanently and silently** — markup present, section rendering as an empty band, no error anywhere. Two causes did exactly that: `content-visibility: auto` on `#projects`/`#publications`/`#contact` (a skipped subtree IntersectionObserver cannot see into — at 390px it left all six animated elements in `#contact` at opacity 0 forever, and every nav-anchor jump landed on a blank section), and `threshold: 0.1` + a negative `rootMargin`, which an element already scrolled past on arrival can never satisfy. The property is gone (see the note in css/styles.css §17) and the reveal is now defensive: `threshold: 0`, a **sweep** that reveals anything whose top has reached the viewport bottom regardless of what the observer reported (re-run on scroll/resize/`hashchange`/`load`, detaching once nothing is pending), an instant reveal for elements above the viewport, everything shown at once under `prefers-reduced-motion` or with no `IntersectionObserver`, and `data-delay` clamped to 320 ms (generate-cards bakes `i * 70`, so publications.html's last paper carried 2520 ms of blank row). The CSS hidden state sits inside `@media (scripting: enabled)` so a no-JS visitor still sees the server-rendered cards, and `@media print` re-reveals everything with `opacity: 1 !important` — **printing scrolls nothing**, so none of the sweep's events fire and Ctrl+P on a freshly-landed page printed 21 of 21 animated elements on the homepage (9 of 12 on the CV) as blank space. Right layout, right page count, missing ink. The fix belongs in CSS rather than in a `beforeprint` handler or a reveal-all timer: opacity is a paint concern, print is a media, and a timer still loses to someone printing immediately. Guarded by `test/css-assets.test.mjs` + the reveal tests in `test/main.node.test.mjs`. **Never hide content behind an observer callback without a fallback that reveals it.** The same trap bites again whenever content is injected *after* `initScrollReveal()` has collected its targets: moving the data modules behind dynamic `import()` made every renderer asynchronous, and the nodes they created carried `data-animate` with nothing observing them — all fourteen project cards and all thirty-seven publications rendered as an empty band, permanently and silently. **Any async render into a `[data-animate]` container must call `revealNewContent(container)`** (js/animations.js), which adds the new nodes to the live observer and sweeps, or shows them outright when no reveal is active. The browser suite caught this; nothing in the static suite could have.

  **The counters were the same trap on `textContent` rather than opacity.** `initCounters()` (js/ui.js) zeroed all three About stats at `DOMContentLoaded` so the count-up had a start value, and restored them only when the observer fired at 60% visibility. Printing scrolls nothing, so Ctrl+P on a freshly-landed homepage printed "0 Countries / 0+ Publications / 0+ Years Exp." — and unlike the reveal, **no stylesheet can fix this**, because the real numbers were gone from the DOM. The `@media print` rule that rescues opacity has no equivalent for text. So the reset now happens *inside* the observer callback, immediately before the count-up that undoes it: the server-rendered value stands until something is actually going to animate it. `prefersReducedMotion()` sets the final value outright, and a missing `IntersectionObserver` leaves the markup alone. **Never overwrite server-rendered content at init for the benefit of an animation that may never run.** Guarded in `test/e2e/content.e2e.mjs`, which asserts under `emulateMedia({ media: 'print' })` *without scrolling first* — scrolling would fire the observer and hide the bug.
- **Section headers**: every `.section-header` is **left-aligned** and its `.section-tag` is a plain uppercase eyebrow — *not* a pill, and never centred. The centred kicker-pill-over-display-title pattern is the single strongest "generated landing page" tell, and the whole site was using it five times over. Sub-page toolbars (`.links-toolbar`, `.links-count`) follow the same left edge.
- **Title + nav conventions**: `<title>`/`og:title`/`twitter:title` use ` — Stefano Masneri` (em-dash) on **project detail pages** and ` | Stefano Masneri` on the **homepage + top-level pages**; keep each tier consistent. `generate-project-jsonld` strips either separator before deriving the JSON-LD `headline`/breadcrumb. Nav links to the CV page use `cv.html` (label "CV") — the homepage no longer has a `#skills` section (removed, see below) or a `#research` id (removed earlier). Every page carries a "Now" nav item (`now.html`), the `.cmd-trigger-hint` ⌘K chip after the nav list, and an Atom `<link rel="alternate">` in the head — a feed reader pointed at any URL on the site should find the feed, not just the homepage. Footer reads "Written by me, coded with Claude and plenty of ☕ in San Sebastián" — the wording deliberately separates authorship of the words from authorship of the code (no Three.js credit — the homepage ships none).

## Things to Avoid

- Don't bypass Vite — production HTML uses `<script type="module" src="/js/main.js">`; data files are imported by main.js, not loaded as standalone scripts
- Don't edit generated files (`data/cv.js`, `data/locations.js`, `js/theme.js`, `data/countries.js`, `data/unesco.js`, `data/links.js`, `data/cnn-activations.js`, `data/cnn-model.json`) or the `<!-- world-map:start … -->` SVG block in `index.html` — regenerate via the relevant script
- **Inline architecture diagrams**: the RAG and brand-stadium diagrams are **inline `<svg class="diagram">` in their project pages**, not `<img src="…svg">`. An external SVG is its own document and cannot read the page's custom properties, so its colours have to be baked in — and they were, across three files, in **three different superseded palettes** (indigo/cyan on `#080c14` for the RAG pair, crimson for brand-stadium). In light mode those were near-black rectangles in a cream page; in dark mode, *cold* blue-black on a warm brown one in accents the ramp never uses. Inlined, `fill="var(--accent)"` resolves like any other declaration, so they follow the palette and the light/dark toggle with **no regeneration step** — the same reason the homepage world map is inline. There is deliberately no generator: once the colours are variables there is nothing to generate. They also asked for `Inter` and `Segoe UI`, neither of which the site loads; they now use the mono stack, at 88% of the original size so the longest label stops overflowing its box. Two SVGs (`rag-query`, `mnist-lenet`) are *also* used as project-hero wallpaper, where a diagram behind a 65–95% scrim came out as grey wash with label text bleeding into the nav. Those files are now **stencils** — background rect removed — painted through `mask-image` with `var(--accent)` via `.project-hero--diagram`, so only their alpha matters. `test/css-assets.test.mjs` fails on a hex literal returning to an inline diagram, or on one reverting to `<img>`.
- Don't hardcode colours — add them to `data/palettes.yaml` and consume via `var(--*)` (CSS) or `THEME` from `js/theme.js` (JS/shaders), so palette switching stays consistent
- Don't colour small text with `var(--accent)` / `var(--accent2)` / `var(--accent-hi)`. Those are brand colours held to WCAG's **3:1 non-text** floor (gradients, borders, pins, glows). Text under 24px needs **4.5:1** and must use `var(--accent-text)` / `var(--accent2-text)`, which `test/contrast.test.mjs` validates against every surface it lands on — including hover states, where `--accent-hi` is *less* contrasty in light mode. Text on an accent **fill** uses `var(--on-accent)`, never `var(--bg)`
- Don't measure a text colour against `--bg` alone. Translucent surfaces **stack**: a card is `text` at 12% over the page, a `--bg-card-hov` chip inside a card composites twice, and cards sit on `bgAlt` as well as `bg` — each step lighter in dark mode. `textSurfaces()` in `test/contrast.test.mjs` enumerates the real set, measured from the rendered page; extend it rather than assuming
- Don't edit the `@theme-generated` block inside `css/styles.css` by hand — it's overwritten by `generate-theme`
- Don't load external fonts, third-party scripts, or any cookie-setting / cross-site tracker — privacy-first. The one permitted external request is the **GoatCounter no-JS analytics pixel** (cookieless, no personal data, image-only — `img-src https://stocastico.goatcounter.com`); keep analytics to that pixel.
- Don't remove `prefers-reduced-motion` checks or accessibility attributes
- Don't commit `.cache/` changes without verifying geocoding results
- Don't add `module.exports` / CJS to anything under `js/` or `data/` — they're ESM
- Don't add a document/window listener or observer in an init without returning a teardown and `_pushTeardown`-ing it (bfcache leak); use `listenerBag()` in js/ui.js
- Don't statically `import` a **data** module (`../data/*.js`) into `js/main.js` either — the code rule below was learned for `europe-map.js` and then not applied to data. All six data modules were static imports, putting **21.3 KB gzip of a 31.3 KB shared bundle (68%)** on all 21 pages: a visitor on `now.html` fetched the UNESCO tree, the 49-entry blogroll, every travel pin, the full CV, 37 publications and 14 projects. Each renderer already gated on a DOM id, so the `import()` moved inside that gate — `main.js` is now 13.1 KB gzip and `now.html` pulls 16.2 KB of JS against 35.9 KB before. Consequence: the render functions take their data as a **required parameter with no default**, because a default has to name the module at the top of the file, which is what put it in the eager graph. `data/locations.js` rides along with the globe/Europe-map imports since both read `globalThis.LOCATIONS` from their constructors. `test/main.node.test.mjs` fails on a static `../data/` import *and* on a missing dynamic one, so deleting the imports does not satisfy it.
- Don't statically `import` a module that only one page uses into `js/main.js` — that puts it in the eager graph of **every** page. `europe-map.js` was imported that way and shipped 10 KB to the twenty pages with no `#europe-canvas`. Single-page modules go behind a dynamic `import()` at their init site, like `globe.js` / `cnn-hero.js` / `mnist-lab.js`
- Don't make `dist/img/` a copy of `img/`. `copyReferencedImages()` in `vite.config.js` copies **only what the built HTML names with an absolute `/img/` URL**, plus all of `img/og/` (one social card per palette — the inactive ones become the referenced one when `active:` changes). The old plugin walked the directory, so Rollup's hashed copy in `dist/assets/` and a verbatim copy both shipped: **28 byte-identical duplicates, 1,378 KB**, on top of **546 KB nothing referenced at all**. `dist/img/` is now 1.2 MB, down from 2.6 MB. The set is *derived* by scanning `dist/**/*.html` rather than hardcoded, so adding a project page needs no edit here. **11 files still ship twice on purpose** (~543 KB) — a hero background is hashed by Rollup *and* named by `og:image`, and pointing `og:image` at the hashed name would change the social-card URL on every build, busting scraper caches for a saving smaller than the problem. `test/css-assets.test.mjs` fails on any image in `img/` that nothing references.
